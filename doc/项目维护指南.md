# http-raw-log 项目维护指南

> 面向项目维护者、发布者和从旧版本升级的使用方。
> 使用方接入、完整配置项、控制台示例和更新日志见根目录 [README](../README.md)。

当前工作区版本：**1.1.0**（以 `gradle.properties` 为准）。

---

## 1. 项目概览

`http-raw-log` 是一个 Spring Boot Starter 形式的 HTTP 原始报文日志工具：

- 通过 Servlet `Filter` 包装请求/响应，把请求行、请求头、请求体、响应状态、响应头、响应体打印到 debug 日志；
- 可选把最近请求写入有界内存，通过 `/httpRawLog/history` 查询；
- 可选按 URI 统计请求次数和平均耗时，通过 `/httpRawLog/statistics` 查询；
- 默认只记录 `content-type` 请求头，不主动记录 cookie、authorization 等敏感头。

它定位为**开发/测试期排障工具**，不建议在生产环境无条件对外开放调试端点。

## 4. 发布到 Maven Central

### 4.1 版本号

版本唯一来源是根目录 `gradle.properties`：

```properties
version=1.1.0
```

发版前先改这里，再打 tag；不要在 `build.gradle` 或 POM 中重复写版本。

### 4.2 准备 GPG 密钥

首次发布需要一对 GPG 密钥（已有可跳过）：

```bash
# 生成密钥（交互式，RSA 2048/4096 均可）
gpg --full-generate-key

# 查看 Key ID
gpg --list-secret-keys --keyid-format LONG

# 导出私钥（armor 文本，供 SIGNING_KEY 使用）
gpg --export-secret-keys --armor <KEY_ID> > private.pgp

# 上传公钥，Central 校验签名时要用
gpg --keyserver keyserver.ubuntu.com --send-keys <KEY_ID>

# 验证公钥已可被检索
gpg --keyserver keyserver.ubuntu.com --search-keys <KEY_ID>
```

注意：

- GPG 2.1+ 不再自动生成 `secring.gpg`，本项目也不需要该文件，直接使用 `private.pgp` 的 armor 文本；
- 私钥只放本机或 CI Secret，禁止提交仓库；
- `keyserver.ubuntu.com` 上传失败时可换 `keys.openpgp.org`、`pgp.mit.edu`。

### 4.3 签名配置

项目使用 Gradle `signing` 插件和 in-memory PGP key。以下两种方式任选：

```bash
# 方式一：Gradle 属性
./gradlew :core:publishAndZip \
  -PsigningKey="$(cat private.pgp)" \
  -PsigningPassword='***'

# 方式二：环境变量
export SIGNING_KEY="$(cat private.pgp)"
export SIGNING_PASSWORD='***'
./gradlew :core:publishAndZip
```

PowerShell：

```powershell
$env:SIGNING_KEY = Get-Content -Raw private.pgp
$env:SIGNING_PASSWORD = '***'
.\gradlew.bat :core:publishAndZip
```

规则：

- 没有密钥时 `signing` 自动跳过，`publishToMavenLocal` 可用；
- 没有密钥时 `publishAndZip` 仍会生成 zip，但**没有 `.asc`，Maven Central 会拒绝**；
- 正式发布必须提供密钥，且公钥已上传到密钥服务器；
- 私钥不要提交到仓库，只放在本机或 CI Secret 中。

### 4.4 生成待上传包

```bash
./gradlew :core:publishAndZip
```

产物：

- `core/build/repo/com/skycong/http-raw-log/<version>/`：POM、jar、sources、javadoc、module 及校验和；
- `core/build/http-raw-log-<version>.zip`：待上传的 Maven Central bundle。

### 4.5 上传

1. 打开 <https://central.sonatype.com/publish>；
2. 选择 **Publish Component**，上传上面的 zip；
3. 等待校验通过（签名、POM、sources/javadoc 齐全）；
4. 点击 **Publish**；
5. 在 <https://central.sonatype.com/artifact/com.skycong/http-raw-log> 确认版本出现。

当前仓库的发布是**手动上传 zip**，Gradle 只负责生成 bundle，不会直接调用 Central API。

## 5. 从 0.9.x / 1.0.x 升级

### 5.1 Spring Boot 3 / Jakarta

1.x 基于 Spring Boot 3，Servlet API 从 `javax.servlet` 迁移到 `jakarta.servlet`。如果项目中有自定义 Filter 或直接引用 Servlet API，需要同步替换：

```text
javax.servlet → jakarta.servlet
```

自动配置入口也从 `spring.factories` 改为：

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

如果曾通过 `spring.autoconfigure.exclude` 排除本库，请确认排除项仍然生效。

### 5.2 不兼容的 API 变更

| 变更 | 处理方式 |
|---|---|
| `HistoryApi.HISTORIES` 静态集合移除 | 注入 `HistoryStore` bean，或调用 `historyStore.snapshot()` |
| `StatisticsApi.statistics(...)` 静态方法移除 | 注入 `StatisticsApi` bean |
| `InMemoryAppender` 移除 | 使用 `HistoryStore` 或自定义 `HistoryRecord` |
| `ResponseWrapper.MAX_LOG_BODY_SIZE` 语义变更 | 保留为 `64KB` 的 deprecated 别名，新代码用 `DEFAULT_MAX_LOG_BODY_SIZE` 或 `getMaxLogBodySize()` |
| bean 名变更 | Filter 注册 bean 名改为 `httpRawLogFilterRegistration`；自定义覆盖时使用同名 bean |

### 5.3 行为变化

| 场景 | 0.9.x | 1.1.0 |
|---|---|---|
| 大响应 | 整包缓冲，超过 4MB 截断客户端响应 | tee 写入，客户端始终收到完整响应；日志只保留前 `maxResponseLogBytes`（默认 64KB） |
| 大请求体 | 业务 body 可能被截断到 4MB | 业务拿到完整原始流；超过 `maxRequestBodyBytes`（默认 64KB）、二进制、压缩时**不包装请求**，日志记 skipped；普通 chunked 有界预读并回放，超限记前缀；form/multipart 未知长度仍跳过 |
| 二进制响应/下载 | 先复制最多 4MB 再丢弃 | 按 content-type/attachment/content-encoding/SSE 跳过捕获，只记元数据 |
| async / SSE | 初始 dispatch 就记录，body 为空、耗时不完整 | `AsyncListener` 在真正完成时记录一次；SSE 不缓存 body |
| 异常请求 | 可能记录 200 且无异常信息 | 记录 500 + 最内层异常类/消息，然后原样抛出 |
| 历史内存 | 只按条数限制，body 可能很大 | 条数 + 总字节（`history.maxTotalBytes`，默认 4MB）+ 单条 body（`history.maxBodyBytes`，默认 32KB）三重限制 |
| `history.maxChars` | `<=3` 不截断 | `<=0` 不截断；`1..3` 直接截断到该长度 |
| 统计 key | 原始 URI，路径参数导致基数无界 | 数字/UUID/长十六进制归一化为 `{id}`，最多 1000 个 key |
| 请求头 | 可能输出 `content-type=null`，顺序不稳定 | 跳过 null/空值，`LinkedHashMap`/`LinkedHashSet` 保序 |

新增配置项：

```properties
com.skycong.http-raw.log.maxRequestBodyBytes=65536
com.skycong.http-raw.log.maxResponseLogBytes=65536
com.skycong.http-raw.log.history.maxBodyBytes=32768
com.skycong.http-raw.log.history.maxTotalBytes=4194304
com.skycong.http-raw.log.console.colors=true
```

旧开关 `com.skycong.http-raw.log=false` 仍兼容，但已废弃，推荐 `com.skycong.http-raw.log.open=false`。

### 5.4 升级验证与回滚

升级后：

1. 启动应用，确认日志级别为 debug；
2. 调用一个普通接口，确认控制台出现 `hLogId`；
3. 调用 `/httpRawLog/history` 和 `/httpRawLog/statistics`（如已开启）；
4. 验证大响应/文件下载客户端内容完整；
5. 验证自定义 `HistoryRecord`/统计代码已改为注入 bean。

回滚：把依赖版本改回 `0.9.16`，重新构建并重启。注意 1.1.0 新增的配置项在旧版本会被忽略。

## 6. 运行行为与限制

### 6.1 请求

- 默认 `maxRequestBodyBytes=64KB`；
- 仅 POST/PUT/PATCH/DELETE 可能带 body；GET/HEAD/OPTIONS/TRACE 直接记录空 body，不写 skipped 标记；
- 有 `Content-Length` 时：超过上限、`Content-Encoding` 非 identity、二进制 content-type、超大 multipart：不包装请求，业务读取原始流，日志写 `[request body skipped: ...]`；
- 没有 `Content-Length`（chunked）时：非 form、非 multipart 请求由 `BoundedRequestWrapper` 预读 `maxRequestBodyBytes + 1` 字节；预读缓冲从 8KB 按需扩容，不会按配置上限预分配；未超限完整记录，超限只记录前缀，剩余字节通过 `SequenceInputStream` 回放，业务仍读到完整 body；`getInputStream()` 始终返回同一个流实例，只能消费一次；
- form-urlencoded / multipart 的 chunked 请求仍跳过：它们需要完整 body 才能正确解析参数/part；
- 小请求体完整缓存并回放，日志字符串再由 `HistoryApi` 按 32KB 截断；
- multipart 小请求由 `FormRequestWrapper` 解析参数；文件内容不写入日志；
- `application/x-www-form-urlencoded` 先缓存原始 body，再自行解析参数；参数解析和日志解码都使用同一套 `charset=`/容器编码规则（显式 GBK 表单不会只在日志里乱码）；没有 `=` 的 flag 参数按 Servlet 语义返回空字符串 `""`，不是参数缺失；
- 业务侧 `getReader()` 使用 `Content-Type` 显式 charset、JSON/XML 缺省 UTF-8、否则容器声明编码（未声明按 Servlet 默认 ISO-8859-1）；只有日志字符串使用 UTF-8 启发式，避免日志组件改变业务读出字符。

### 6.2 响应

- `ResponseWrapper` 是 tee 语义：先写客户端，再旁路复制日志；
- 默认日志上限 64KB，可配；
- `image/*`、`audio/*`、`video/*`、`font/*`、`application/octet-stream`、pdf/zip/gzip/wasm/protobuf 等不捕获；
- `Content-Disposition: attachment`、非 identity `Content-Encoding`、`text/event-stream` 不捕获；
- 其他文本响应按响应字符集解码，超过上限追加 `[response body truncated ...]`。
- 字符集选择顺序：`Content-Type` 的 `charset=` → JSON/XML 缺省 UTF-8 → 容器声明的非 ISO-8859-1/US-ASCII 编码 → 对 ISO-8859-1/US-ASCII/未声明做严格 UTF-8 校验 → 回退声明值。Tomcat 对无 charset 的 JSON 响应默认返回 ISO-8859-1，但实际 body 是 UTF-8，日志按上述规则解码。
- 响应头默认记录 `content-type`；Tomcat 通过 `setContentType` 设置的值可能不在 `getHeader("content-type")` 中，header 为空时回退 `getContentType()`。
- `sendError` 会清空响应缓冲；wrapper 同步清空日志缓冲，并记录 `[sendError 404: message]` 摘要。容器随后渲染的错误页正文不经过本 filter 的 dispatch，因此仍不捕获。

### 6.3 异步与异常

- `Callable`、`DeferredResult`、`SseEmitter` 通过 `AsyncListener` 的 `onComplete/onError/onTimeout` 记录，`AtomicBoolean` 去重；
- 异步开始后 filter 的 `finally` 不立即写历史；
- 业务异常仍记录，状态按 500 处理，响应体追加最内层异常摘要后重新抛出。

### 6.4 历史与统计

- `history=0`（默认）：只输出控制台，`/httpRawLog/history` 仍存在但返回空数组；
- `history>0`：内存历史，受条数和 UTF-8 字节数双重限制；
- `/httpRawLog/history?hLogId=...` 按 id 查询；
- `/httpRawLog/history/{hLogId}` 单条详情（body 仍受 `history.maxBodyBytes` 限制，不是无限原文）；
- 自定义 `HistoryRecord` bean 后，默认 `HistoryApi` 不再创建，`/httpRawLog/*` 的历史端点由使用方自行决定；
- `/httpRawLog/statistics?type=total&sort=desc` 返回统计；URI 已归一化。

### 6.5 安全

- 默认只记录 `content-type` 请求头，**不记录 cookie/authorization**；
- 如果使用方把 `cookie`、`authorization`、`set-cookie` 加入 `com.skycong.http-raw.log.headers`，这些值会明文进入控制台、内存历史和查询接口；
- **脱敏功能尚未实现**（原 P0-5 暂缓）；生产环境如必须记录敏感头，请自行在 `HistoryRecord` 实现中脱敏；
- `/httpRawLog/*` 没有内置鉴权，需由宿主应用通过 Spring Security、网关白名单或 `open=false` 控制；
- 建议只在开发/测试环境开启，或限制内网访问。

## 7. 已知限制与后续

| 项目 | 现状 | 影响/后续 |
|---|---|---|
| 敏感信息脱敏 | 未实现 | 默认头安全，但配置敏感头会明文；后续可加 header 白名单/JSON 掩码/Redactor SPI |
| gzip/deflate 请求 | 直接跳过，不解压 | 日志无 body；避免解压炸弹，优先保持跳过 |
| chunked form/multipart | 需要完整 body 解析，仍然跳过 | 日志只写 skipped 标记；普通 JSON/text chunked 已支持 |
| 错误页 body | `sendError` 已记录状态/消息，但容器渲染的错误页正文不捕获 | 记录 `[sendError ...]` 摘要；错误页正文由日志框架/容器记录 |
| 大 multipart | 超过上限跳过解析 | 文件内容不记录；业务仍可正常上传 |
| multipart 二次解析 | 小 multipart 可能被 `FormRequestWrapper` 和 Spring resolver 各解析一次 | 功能通常正常，但大表单/高并发需关注开销；后续复用 parts 或跳过 body 捕获 |
| `getContentLength()` | `RequestWrapper` 返回缓存 body 字节数；`BoundedRequestWrapper`（chunked）保留容器 `-1` | 业务代码不要依赖该值做协议判断 |
| 配置元数据 | 仍手写 `spring-configuration-metadata.json`，但有 key + description 一致性测试守卫 | 新增 `Constant` 配置项未补 metadata，或描述仍写旧行为（如“长度未知时不再包装”）时测试失败；后续可迁移 `@ConfigurationProperties` |
| 指标 | 无 Micrometer 计数器 | 无法直接观测截断/丢弃次数；后续加 timer/counter |
| 历史详情 | 仍受 32KB body 限制 | 不是完整原文；如需完整回放需另接文件/对象存储 |
| 文件日志关联 | `FileAppender` 依赖日志文件格式 | 默认关闭（需显式配 `appLogFilePath` 且 `history>0`） |
| 自定义 Filter 覆盖 | 自动配置按 bean 名 `httpRawLogFilterRegistration` 判断 | 自定义注册时保持同名，避免注册两个 filter |
| 压测 | 未执行 1GB 上传/100MB 下载/长连接 SSE | 上线前建议在预发环境补压测 |

P2 方向（暂未实现）：JSONL 文件 sink、OTLP/日志平台 sink、按比例/错误/慢请求采样、查询页面与请求回放、基准测试；`Automatic-Module-Name` 已在 1.1.0 提供。

## 8. 常见问题

### Q1：接入后没有日志？

依次检查：

1. `logging.level.com.skycong.httprawlog=debug`；
2. `com.skycong.http-raw.log.open` 不为 `false`；
3. URI 没有被 `url.exclude` 或默认静态资源规则排除；
4. `history=0` 只影响内存历史，不影响控制台；
5. 请求是否因大 body/二进制/压缩被标记为 skipped；
6. 响应是否是二进制/附件/SSE，因而不记录 body。

### Q2：客户端收到的响应被截断了吗？

不会。1.1.0 起响应是 tee 写入，客户端始终收到完整响应；只有日志保留前 `maxResponseLogBytes`。

### Q3：请求体很大，业务会收到不完整内容吗？

不会。超过 `maxRequestBodyBytes` 时 filter 不包装请求，业务直接读原始流；日志只写 skipped 标记。小请求体会完整缓存并回放。

### Q3.1：GET/HEAD 的 request body 为什么是空的？

GET/HEAD/OPTIONS/TRACE 通常没有 body，1.1.0 起直接记录空字符串，不再显示 `[request body skipped: unknown content-length]`。只有 POST/PUT/PATCH/DELETE 在长度未知/超限/二进制时才会写 skipped 标记。

### Q4：`history=0` 为什么还能访问 `/httpRawLog/history`？

`history=0` 表示不存历史，端点仍存在并返回空数组，便于统一前端/脚本；如果不需要端点，设置 `open=false`，或自定义 `HistoryRecord` 使默认 `HistoryApi` 不创建。

### Q5：还能用 Spring Boot 2.x / Java 8 吗？

不能。1.x 要求 Spring Boot 3.x + Java 17 + `jakarta.servlet`；请继续使用 `0.9.x`。

### Q6：为什么统计里看到 `{id}`？

统计会把数字、UUID、长十六进制路径参数归一化为 `{id}`，避免 `/order/1`、`/order/2` 无限增长；最多保留 1000 个 URI key。

### Q7：发布时没有 GPG 会怎样？

`publishToMavenLocal` 正常；`publishAndZip` 也能生成 zip，但没有 `.asc`，Maven Central 会拒绝。正式发布必须配置 `SIGNING_KEY`/`SIGNING_PASSWORD`（或 `-PsigningKey/-PsigningPassword`）。
